# 4. Method description

The task is video question answering over short monocular clips: each item supplies one video and
asks for a physical quantity in a requested unit (m, cm, mm, m/s, cm/s, m/s², cm/s²), and the answer
must be a single finite number followed by that unit. The submitted file answers all 3,289 items
covering 568 videos. Every item is processed on its own: its video and question are the only inputs
to its prediction.

The model is the public checkpoint `MirroS-Lab/Code-as-World-VL-4B` at revision
`104afb28b4f1eee1d1131a50281be590e930babb`, a 4B-parameter vision-language model whose card names
`Qwen/Qwen3.5-4B` as upstream. Adaptation is pure LoRA with r=16, α=32, dropout 0.05 and bias=none
on twelve projection modules per layer. The trainer asserts that every trainable parameter name
contains `lora_`, and builds its optimizer only from those parameters, so the base weights are never
updated and no merged checkpoint exists. The submitted predictions load the base plus the single
final adapter; nothing else was loaded at inference time.

Training was one continuation epoch starting from a measured 0.863 adapter, itself the product of
earlier rounds and included here as the initializer. Settings were one epoch over 3,289 rows at
learning rate 2e-5, gradient accumulation 8 (412 optimizer steps), seed 1, bfloat16, gradient
checkpointing, warmup fraction 0.03, weight decay 0, gradient clipping 1.0, and answer-only loss, so
the video and question tokens were masked and only the target answer tokens contributed. Each item
was read as 16 decoded frames. Training took 10,114 s on one RTX 6000D. The targets are MAIN7493
pseudo-labels generated by a Track A reference model that scored 0.874.

Inference decodes each item's own video to 32 frames sampled at 2 fps with `max_pixels=262144`
(reduced to the largest even count available for shorter clips), combines them with the question and
requested unit through the training chat template with thinking disabled, and generates greedily for
at most 64 new tokens. Nothing is batched across items beyond the individual request, and no answer,
statistic or context from another item is available to the model.

Every generation is validated as a whole answer before acceptance: the text must contain exactly one
finite number, its unit must be the requested unit, and generation must stop with a known EOS token
without reaching the token limit. Non-finite values, negative scalars for non-negative quantities and
float underflow are rejected. If the first attempt fails, one clarification prompt is issued in the
item's own requested unit and validated the same way; 4 of 3,289 items used that retry and none
remained unresolved.

Predictions and the raw generation journal were written and hashed before any comparison with the
teacher labels. A fresh-process validator replayed every recorded attempt through the same
answer-contract code and confirmed row order, metadata, adapter identity and CSV hash without
importing the primary validator. The submitted CSV is byte-identical to the frozen predictions, with
SHA-256 `1216ece8fae28f39431a719973794381d29e813214eacbcb66a1da82cb5d5b56`. Each prediction was
produced independently from its own item's inputs, as stated in `5.Declaration.md`.

The official portal result is average MRA 0.866 (Track B · Open weight, pass; S2 0.860, D2 0.887,
S3 0.851, D3 0.866; invalid 0.0%; 3,010 matched, 0 missing), up from 0.863 for the initializer, on
8 × NVIDIA RTX 6000D with the jobs on GPU 0. On 2026-10-28 the delivered code was re-executed on that
server: the 8-question smoke run and the full 3,289-question rerun finished with no parse failures
and reproduced the CSV, the generation journal and the frozen predictions byte-for-byte, and the
16-frame training cache was rebuilt with all 568 hashes matching. The one-epoch training run itself
was not repeated, and exact reproduction is demonstrated on the recorded host and library set;
different GPU or library versions may perturb bfloat16 results.
